# ADR 0024: Lyriaへ確認済みの読みと曲構成を渡す

Date: 2026-10-12

## Status

Proposed

2026-10-12のチャットで、ユーザーが歌詞作成からの刷新、ジャンルと歌声の選択、自動で作成する読みの修正、編集後の一括更新を含む計画に「PLEASE IMPLEMENT THIS PLAN」と指示した。計画の指定どおりProposedとして記録する。実APIの歌唱品質は別の受け入れ確認を必要とする。

## Context

文字起こしと歌詞作成はユーザーの評価で良好だが、曲生成時に漢字の読み間違いが多い。現行コードはLyria 3.5へ英語の固定指示と漢字の歌詞を渡し、読みを指定するデータを持たない。返却歌詞のテキスト一致だけでは実際の歌唱の読みを検証できない。

## Decision

[ADR 0010](0010-google-audio-quality-trial.md)のモデル候補と累積予算、[ADR 0011](0011-cloudflare-free-audio-runtime.md)の実行先を維持する。Google公式の[プロンプトガイド](https://ai.google.dev/gemini-api/docs/lyria-prompt-guide)と[音楽生成仕様](https://ai.google.dev/gemini-api/docs/music-generation)に従い、日本語の音楽指示、`Lyrics:`、Verse・Pre-Chorus・Chorus・Bridgeの構造タグを使用する。

方式2の歌詞作成と読み更新には、同じGemini 3.5 Flash-Liteの `thinking_level: high` を使用する。既定のminimalで地名・日付の読みと文字の誤りが実検証で出たため、地域・日付と日数・読みの脱字を同じ呼び出し内で照合する。思考を含む出力上限は16384トークンとし、[公式仕様](https://ai.google.dev/gemini-api/docs/thinking)に従う。

利用者は歌詞作成前に6種類のジャンルと男性・女性・おまかせの歌声を選ぶ。テンポ・楽器は固定プリセットとする。同じ歌詞作成呼び出しで表示歌詞、出典、曲構成、歌唱用のかな歌詞を作り、利用者が確認・修正できるようにする。本文の編集は該当ブロックの読みを無効にする。読み更新ジョブは保存済みリビジョンを固定し、未作成の読みだけを補い、再確認を待つ。

生成方式と曲設定を歌詞リビジョン・ジョブへ保存し、歌詞作成のキャッシュ識別にも含める。旧データは方式1で維持し、新しい曲設定付きの歌詞作成を方式2とする。読み更新も既存の有料試行台帳・実行権取得・結果保存・照合待ちを使う。本文編集時の自動API呼び出しや、有料POSTの自動再送は行わない。

かな歌詞の効果は検証仮説であり、Googleが発音を保証する仕様とは扱わない。丸括弧は公式ガイドでバックボーカルを表すため、漢字と括弧のふりがなを併記する案は見送る。完全自動の読み判断は固有名詞の修正ができないため、利用者が選んだ確認・修正方式を採用する。詳細なテンポ・楽器の選択は今回の選択範囲に含めない。

## Consequences

- 利点: 表示歌詞を保ったまま読みを指定でき、曲設定と歌詞の承認内容を再開時も追跡できる。
- 受け入れる欠点: 編集後の読み更新には追加のAI費用が発生する。high推論は既定設定より処理時間とトークン費用が増える。かな表記でも歌唱の誤り・脱落が起こり得る。旧ジョブは新方式へ途中で切り替わらない。
- 確認: 旧方式・新方式を同じ歌詞で各3回比較し、新方式で対象語の誤読・追加・脱落がないことを試聴で確認する。今回の試行は最大2ドル、既存の累積10ドル以内とし、移管済みPoC台帳は再開しない。
